# Design Rules — общие правила разработки игр «Лесной школы»

Этот документ фиксирует практические правила, выработанные при создании сайта. Он дополняет `GAME_SPEC.md` и `AGENTS.md`: спецификация описывает продукт, а здесь описано, **как проектировать и реализовывать игровые сцены, поведение, графику, звук и адаптивность**.

## 1. Основной принцип

Игра считается готовой, только когда ребёнок может самостоятельно пройти полный цикл:

1. открыть карточку игры;
2. прочитать правила;
3. выполнить 10 заданий;
4. получить понятную реакцию на каждое действие;
5. увидеть победу или поражение и награду;
6. повторить игру либо вернуться на главную.

Персонаж обязан участвовать в механике. Статичная картинка рядом с кнопками не считается игровым поведением.

## 2. Единая структура игрового модуля

Каждая игра автономна и хранит собственные компоненты, данные и ресурсы:

```text
src/games/<game>/
  components/    игровая сцена и локальные UI-компоненты
  data/          типизированный банк заданий
  assets/        фоны, персонажи и предметы
  audio/         музыкальная тема и локальные звуковые ресурсы
  styles/        стили только этой игры
  tests/         тесты механики и контента
```

Правила границ:

- игры не импортируют компоненты, данные, стили или ассеты друг друга;
- педагогический контент не хранится внутри JSX или TypeScript-массивов;
- все банки заданий обязательно хранятся в отдельных `.json`-файлах внутри `data/`;
- в `shared` выносится только то, что действительно используется несколькими играми;
- игровой компонент экспортирует корневую сцену и принимает общие callbacks завершения, выхода, правил и звука;
- backend, база данных, аккаунты, CDN и обязательные сетевые запросы не используются.

### 2.1. Универсальное правило хранения игровых данных

Все педагогические данные любой игры серии обязательно хранятся в JSON. Это относится к словам, предложениям, изображениям-заданиям, категориям, правильным ответам, вариантам ответа, подсказкам и параметрам сложности.

```text
src/games/<game>/data/
  tasks.json       основной банк заданий
  tasks.ts         типы, валидация, загрузка и генератор сессии
```

Обязательные правила:

- таблицы заданий создаются в `.json`, а не внутри JSX, TS/TSX-компонентов или CSS;
- каждый объект имеет стабильный уникальный строковый `id`;
- JSON содержит только сериализуемые данные: строки, числа, логические значения, массивы и обычные объекты;
- функции, React-компоненты, вычисления и обработчики событий в JSON не помещаются;
- правильный ответ и необходимые параметры проверки должны однозначно следовать из записи JSON;
- ссылки на локальные изображения или звуки задаются идентификатором либо относительным путём, но сами импорты ресурсов выполняются в TypeScript;
- формат банка описывается TypeScript-интерфейсом рядом с загрузчиком;
- после импорта JSON код проверяет обязательные поля, допустимые значения, уникальность `id` и достаточный размер банка;
- производные значения вычисляются в `tasks.ts`, чтобы не хранить противоречащие копии данных;
- генератор сессии получает банк как вход, перемешивает или выбирает элементы и не изменяет исходный массив;
- UI-компонент получает уже подготовленное задание и не знает полный список контента;
- добавление нового задания должно требовать изменения только JSON, если схема и механика не меняются;
- JSON входит в локальную production-сборку и не загружается с внешнего сервера во время игры.

Рекомендуемые минимальные поля общей записи:

```json
{
  "id": "stable-task-id",
  "prompt": "Текст или условие задания",
  "answer": "Правильный ответ",
  "options": ["вариант 1", "вариант 2", "вариант 3"],
  "difficulty": 1
}
```

Конкретная игра может использовать специализированные поля вместо `prompt` и `answer`, например `word` + `missingIndex`, `syllables` или `words` + `correctOrder`. Поле `difficulty`, если применяется, имеет заранее описанную шкалу и не подменяет динамическую сложность механики.
## 3. Игровая сессия и подсчёт результата

- Одна сессия содержит ровно 10 уникальных заданий.
- Выборка формируется из банка заданий без повторов.
- Если цель игры ещё не достигнута после зачётных заданий, весь один раз перемешанный банк можно повторять по кругу; повторные круги не изменяют уже зафиксированный зачётный результат.
- Ошибка обычно не блокирует текущее задание: ребёнок может попробовать снова.
- В итоговый `score` попадают задания, выполненные верно с первой попытки.
- Каждое неверное действие увеличивает `mistakes`.
- Во время показа результата повторный ввод блокируется, чтобы одно действие не учитывалось дважды.
- Незавершённая сессия не сохраняется и не выдаёт награду.
- Завершённая сессия получает `outcome: "win" | "loss"`.

Общий контроллер сессии отвечает только за индекс, результат, число ошибок и состояния `idle/correct/wrong`. Правила победы, поражения и специальный прогресс остаются внутри конкретной игры.

Награды:

- попытки не ограничены;
- победа повышает уровень на 1;
- поражение понижает уровень на 1, но не ниже нуля;
- итоговое сообщение явно показывает исход и изменение уровня.

### 3.1. Контент «Лягушки на болоте»

Словарный банк хранится только в `src/games/frog/data/words.json` по общему правилу раздела 2.1 и не дублируется в JSX или TypeScript-массиве. Минимальный формат записи:

```json
{
  "id": "machine",
  "word": "машина",
  "missingIndex": 1,
  "options": ["а", "о", "и"]
}
```

Правила словарного банка:

- в рабочем банке находится 20 слов с уникальными `id`;
- `missingIndex` — индекс скрываемой буквы с нуля;
- правильная буква всегда вычисляется как `word[missingIndex]`, а не хранится вторым независимым полем;
- `options` обязательно содержит правильную букву и педагогически правдоподобные варианты;
- перед добавлением слова вручную проверяются орфография, ударение и именно та позиция, которую допустимо скрывать;
- скрытая форма строится программно заменой одной буквы на `_`;
- буквы и слова остаются HTML-текстом, не запекаются в изображение;
- на каждом задании создаются ровно семь мух: правильная буква, заданные варианты и случайные уникальные буквы русского алфавита;
- правильная буква гарантированно присутствует, а одинаковые буквы не дублируются.

Текущий обязательный набор скрытых форм:

| Слово | Форма в игре | Ответ |
|---|---|---|
| машина | `м_шина` | а |
| собака | `с_бака` | о |
| ворона | `в_рона` | о |
| карандаш | `к_рандаш` | а |
| берёза | `б_рёза` | е |
| воробей | `в_робей` | о |
| сорока | `с_рока` | о |
| мороз | `м_роз` | о |
| девочка | `дев_чка` | о |
| ученик | `уч_ник` | е |
| тетрадь | `т_традь` | е |
| медведь | `м_дведь` | е |
| лисица | `л_сица` | и |
| заяц | `за_ц` | я |
| молоко | `м_локо` | о |
| город | `гор_д` | о |
| дорога | `д_рога` | о |
| яблоко | `ябл_ко` | о |
| картофель | `к_ртофель` | а |
| пальто | `п_льто` | а |

### 3.2. Порядок слов и зачёт

- При запуске все 20 слов один раз перемешиваются алгоритмом Fisher–Yates.
- Игра последовательно проходит весь перемешанный массив без повторов.
- После последнего слова используется тот же порядок с начала: индекс вычисляется по модулю длины массива.
- Новое перемешивание внутри текущей попытки запрещено, поэтому ребёнок гарантированно увидит все слова перед повтором.
- Первые 10 показанных слов являются зачётными и определяют `correct`, `percent` и результат первой попытки.
- Если из-за ошибок лягушка ещё не дошла до короны, следующие слова продолжаются по массиву, но не меняют уже зафиксированный зачётный результат.
- Победа наступает только при достижении десятой позиции и короны.
- Ошибка отодвигает лягушку на одну позицию. Ошибка на позиции 0 завершает текущую попытку поражением.
- После победы или поражения ребёнок может начать новую попытку без ограничений.

### 3.3. Динамическая сложность мух

Сложность определяется текущей позицией лягушки на дорожке, а не номером слова, числом показанных заданий или общим количеством ошибок.

```ts
speedMultiplier = 1 + clamp(progress, 0, 10) * 4 / 10
```

Контрольные значения:

| Позиция | Коэффициент скорости |
|---:|---:|
| 0 | `×1` |
| 1 | `×1.4` |
| 5 | `×3` |
| 9 | `×4.6` |
| 10 | `×5` |

- Верный ответ увеличивает `progress` на 1 и сразу ускоряет уже летящих мух.
- Ошибка уменьшает `progress` на 1 и сразу замедляет уже летящих мух.
- При изменении сложности текущие координаты, направления и взаимное расположение мух сохраняются: объекты нельзя телепортировать или пересоздавать.
- Меняется модуль вектора скорости; дальнейшая случайная смена направления использует новый коэффициент.
- Итоговая скорость дополнительно масштабируется от размера игрового фрейма, чтобы ощущаться сопоставимо на desktop и телефоне.
- При `prefers-reduced-motion` движение может быть остановлено или существенно сокращено без изменения правил ответа.
## 4. Обратная связь на действие

Каждый ответ должен подтверждаться сразу несколькими способами:

- изменением состояния объекта;
- движением персонажа или предмета;
- знаком `✓` или `×`;
- коротким звуком;
- краткой надписью, если без неё смысл неочевиден.

Нельзя передавать смысл только цветом. Красный и зелёный дополняются знаком, движением и звуком.

Рекомендуемый порядок реакции:

1. зафиксировать выбранный объект;
2. проиграть короткий звук нажатия;
3. выполнить основную анимацию действия;
4. показать успех или ошибку;
5. изменить прогресс;
6. после короткой паузы открыть следующее задание.

Сообщения не должны зависать. Короткая реакция обычно видна около `500–900 ms`, затем удаляется. Таймеры очищаются при смене задания и размонтировании компонента.

## 5. Персонажи и анимация

- Анимация объясняет действие, а не служит бесконечным украшением.
- Персонаж явно берёт, несёт, укладывает, ловит или перемещает игровой объект.
- Основная поза не должна дёргаться при смене кадров.
- Для сложных 3D-персонажей предпочтительны заранее отрисованные ракурсы одинакового размера и с одинаковой точкой опоры.
- Нельзя имитировать новый ракурс грубым CSS-вращением готового растра, если меняется перспектива тела.
- Зеркальное отражение допустимо для симметричных левых/правых состояний.
- Анимация ответа должна закончиться раньше перехода к следующему заданию.
- При `prefers-reduced-motion` сокращаются повторяющиеся движения, но игровое состояние и смысл реакции сохраняются.

### Проверенный шаблон слежения персонажа

- На компьютере персонаж получает направление от `pointermove` и продолжает следить за мышью.
- Координата курсора переводится в дискретный индекс подготовленного спрайта.
- На телефоне постоянного курсора нет: нужный ракурс выбирается в `pointerdown` по центру нажатого объекта **до** основной анимации.
- После завершения touch-действия персонаж возвращается в центральную позу.
- Событие `pointerleave` от touch не должно преждевременно сбрасывать выбранный ракурс.
- Тип последнего указателя хранится через `ref`, чтобы не вызывать лишние рендеры.

## 6. Движущиеся объекты

Для свободно летающих или плавающих целей используется собственная игровая область, а не весь документ.

- Координаты хранятся относительно области движения.
- После изменения размера окна позиции пересчитываются пропорционально новой области.
- Объекты отражаются от границ и не выходят за них.
- Запрещённые зоны персонажа, задания и крупных декораций учитываются в расчётах движения.
- Объекты могут частично перекрываться, но не должны полностью закрывать друг друга.
- При выборе нового направления менее занятые сектора получают больший вес.
- Не использовать фиксированные «полосы» для разных объектов: движение должно охватывать всю разрешённую область.
- Скорость может постепенно расти со сложностью, но остаётся управляемой на touch-экране. Для лягушки применяется точная формула из раздела 3.3: успех ускоряет, ошибка замедляет.
- Размер hit-area — не менее `44×44 px`, даже если визуальный объект меньше.
- Диагностические границы областей разрешены при разработке, но удаляются из production.

## 7. Векторная анимация между двумя объектами

Для языка, луча, верёвки или траектории используются фактические DOM-координаты:

```text
start = скрытая точка действия персонажа
end   = фактический центр выбранного объекта
dx    = end.x - start.x
dy    = end.y - start.y
length = hypot(dx, dy)
angle  = atan2(dy, dx)
```

Элемент начинается строго в `start`, поворачивается на `angle` и масштабируется только вдоль `length`. Толщина привязывается к размеру персонажа или игрового фрейма. Слой проходит под персонажем, чтобы начало выглядело естественно скрытым ртом или лапой. Захваченный объект движется обратно по тому же вектору.

## 8. Адаптивный игровой фрейм

Сцена имеет единое координатное пространство и сохраняет пропорции исходной иллюстрации.

- Для горизонтальных игр используется фиксированное `aspect-ratio` исходного фона.
- Фрейм вписывается в доступный viewport целиком, без обрезания ключевых объектов.
- Фон, персонажи, предметы, язык и интерактивные объекты масштабируются от одного фрейма.
- Для размеров внутри сцены предпочтительны container query units (`cqw`), а не `vw`: тогда размер зависит от игры, а не от браузерного окна.
- Внешняя незанятая область использует приглушённую тематическую версию фона, а не случайную однотонную полосу.
- Страница игры не должна получать случайную вертикальную или горизонтальную прокрутку.
- При resize пересчитываются не только размеры, но и координаты движущихся объектов.
- Проверяются минимум: `360 px`, мобильный портрет, мобильный альбомный режим, обычный desktop и низкое широкое окно.

### Элементы, связанные со шрифтом

Если декоративная плашка должна расти вместе с надписью:

- `font-size` задаётся от ширины игрового контейнера;
- ширина плашки задаётся в `em` от этого шрифта;
- пропорции изображения фиксируются через `aspect-ratio`;
- текст размещается отдельным абсолютным слоем `inset: 0` с `display: grid; place-items: center`;
- центр текста, центр плашки и центр игрового фрейма проверяются геометрическим E2E-тестом.

Не растягивать растровую плашку по высоте содержимого: это искажает изображение при изменении масштаба.

## 9. Слои интерфейса

Рекомендуемый порядок слоёв:

1. фон сцены;
2. туман, вода и декоративные частицы;
3. игровые цели;
4. действие между персонажем и целью;
5. персонаж, скрывающий начало действия;
6. знаки результата и короткие сообщения;
7. системные кнопки игры.

Общая игровая оболочка показывает только три компактные кнопки поверх сцены:

- слева — домой;
- справа — правила;
- справа — единые настройки звука.

Не дублировать очевидный прогресс отдельными строками вида «Задание 1 из 10», если он уже показан внутри игровой механики.

### 9.1. Титульная страница серии

Титульная страница оформляется как единая сказочная лесная сцена, но остаётся настоящим адаптивным интерфейсом.

- Фоновая иллюстрация создаёт атмосферу и естественное обрамление; она не содержит текста, кнопок, карточек, логотипов или персонажей.
- Фон хранится локально в `src/app/assets` как оптимизированный WebP и входит в общую предзагрузку критических ресурсов.
- Текст, профиль, настройки звука, карточки и действия реализуются только HTML/CSS/React поверх фона.
- Верхняя панель стилизуется под тёмное дерево с тёплой рамкой, логотипом слева и общими действиями справа.
- Главный заголовок расположен в спокойной светлой части композиции и остаётся читаемым без запекания в растр.
- На desktop одновременно показываются три игровые карточки; каждая выглядит как отдельная иллюстрированная глава общей книги.
- Карточка состоит из локальной фоновой сцены игры, локального изображения персонажа и отдельной светлой текстовой части.
- Силуэт карточки не прямоугольный: верх выполнен широкой полукруглой аркой с плавными плечами и двойным контуром; центральная эмблема перекрывает рамку, а пергаментная часть заходит на иллюстрацию дугой.
- Эмблемы отражают механику игры: кувшинка для лягушки, жёлудь для белочки и бревно для бобра; абстрактные точки и геометрические символы не используются.
- На широком экране основной заголовок сохраняется одной строкой; перенос разрешён только на планшете и телефоне.
- Отдельная плашка с названием учебного навыка на титульной карточке не показывается: остаются название игры, короткое описание и две кнопки.
- Кнопки на карточках имеют плавно неровный ручной контур: асимметричные радиусы, немного различающийся наклон и внутренний кант. Идеально ровные прямоугольники и одинаковые капсулы не используются.
- Фигурная рамка дополнена асимметричными выступающими лесными элементами по бокам и снизу; они наследуют цвет конкретной игры и не уменьшают интерактивную область.
- Нижняя деревянная табличка использует тёмное дерево и контрастный кремовый текст без полупрозрачной текстуры поверх букв и без размытой тени.
- Игры различаются цветом рамки и основной кнопки: зелёный для лягушки, янтарный для белочки, голубой для бобра.
- Вся карточка запускает игру и доступна с клавиатуры; кнопка «Как играть» остаётся отдельной и не запускает игру.
- Декоративные эмблемы, дерево, мох, пергамент и мягкие внутренние тени поддерживают объём, но не перекрывают контент.
- Нижний девиз «Учись • Играй • Открывай» размещается по центру на отдельной неровной деревянной табличке; сплошная полоса по ширине страницы запрещена.
- На планшете сетка может становиться двухколоночной, на телефоне — одноколоночной; профиль упрощается до аватара, но звук и основные действия сохраняются.
- Минимальная ширина `360 px`; текст и кнопки не должны выходить за карточку, а фон не создаёт горизонтальную прокрутку.
- При `prefers-reduced-motion` отключаются декоративные частицы и сокращаются подъёмы карточек.
- Нельзя использовать изображение всего интерфейса как фон: это ломает адаптивность, доступность, локализацию и кликабельность.
## 10. Изображения и ImageGen

- Все production-ассеты лежат внутри директории своей игры.
- Фон обычно сохраняется как оптимизированный WebP без текста.
- PNG/WebP с прозрачностью применяются для персонажей и предметов.
- Текст, буквы, числа и учебные ответы не запекаются в картинку: они остаются HTML-текстом.
- Это позволяет менять задания, поддерживать доступность и корректно масштабировать шрифт.
- Для удаления технического chroma-key используется мягкая маска, despill и проверка прозрачных углов.
- После обработки удаляются промежуточные файлы, а в проекте остаётся только финальный оптимизированный ассет.
- Новый файл получает осмысленное имя с версией; существующий финальный ресурс не перезаписывается без явного решения.
- Графика одной серии сохраняет единый свет, материал, насыщенность и степень 3D-стилизации.

## 11. Предзагрузка ресурсов

Критические изображения загружаются и декодируются до показа игровой сцены:

- фон;
- основные спрайты персонажа;
- интерактивные предметы;
- декоративные панели, влияющие на компоновку.

Пока ресурсы не готовы, показывается единый экран загрузки. Нельзя сначала показывать буквы и hit-area, а затем подставлять фон и персонажа. Ошибка загрузки отдельного изображения не должна навсегда блокировать приложение.

## 12. Звук

- Используется один общий аудиоменеджер.
- У каждой игры своя музыкальная тема, но настройки общие для всего проекта.
- Обязательные эффекты: нажатие, основное действие, правильный ответ, ошибка, награда и завершение.
- `AudioContext` создаётся или возобновляется только после пользовательского действия — это требование политики autoplay браузеров.
- Ошибка `play()` фоновой музыки обрабатывается без падения приложения.
- Есть общий выключатель и отдельные уровни музыки и эффектов.
- Без звука игра остаётся полностью проходимой.

## 13. Управление и доступность

- Основной ввод реализуется через Pointer Events, чтобы одна логика работала для мыши, пера и touch.
- Перетаскивание всегда дублируется обычным нажатием.
- Клавиатурный пользователь может выбрать, переместить и подтвердить объект.
- Нативные кнопки предпочтительнее `div` с искусственным click-handler.
- Все кнопки имеют понятный `aria-label`, видимый фокус и состояния `disabled`.
- Минимальный размер интерактивной зоны — `44×44 px`.
- Во время drag блокируется только конфликтующая прокрутка, а не вся доступность страницы.
- Инструкция доступна и с карточки, и из самой игры.

## 14. Хранение профиля

Используется один версионированный ключ `forest-school:v1`.

Завершённая запись сессии содержит как минимум:

```ts
interface SessionRecord {
  gameId: 'frog' | 'squirrel' | 'beaver'
  modeId: string
  completedAt: string
  correct: number
  total: number
  percent: number
  mistakes: number
  outcome: 'win' | 'loss'
}
```

Правила хранения:

- сохраняется только завершённая сессия;
- старые записи дополняются безопасными значениями по умолчанию;
- устаревшие поля `totalHearts` и `session.hearts` удаляются при загрузке и больше не записываются;
- числовые значения нормализуются и не могут стать отрицательными;
- повреждённый JSON не ломает запуск;
- сброс профиля требует подтверждения;
- звук хранится в том же профиле и применяется ко всем играм.

## 15. Тестирование геометрии и поведения

Проверять нужно не только наличие элементов, но и фактическое поведение.

Unit/component-тесты:

- 10 уникальных заданий;
- подсчёт первой попытки и ошибок;
- проценты, ошибки, победа/поражение и изменение уровня;
- миграция старого `localStorage`;
- формула скорости лягушки: `×1` на позиции 0, `×3` на позиции 5 и `×5` на позиции 10;
- формы профиля и критические состояния UI.

Playwright desktop/mobile:

- три карточки и инструкции;
- полный вход в каждую игру;
- число интерактивных объектов;
- движение персонажей и объектов;
- границы разрешённой области;
- отсутствие overflow;
- сохранение пропорций после resize;
- геометрическое совпадение центров связанных элементов;
- mouse tracking и touch-поведение проверяются отдельно;
- после touch-действия персонаж возвращается в исходную позу, если это предусмотрено механикой;
- отключённый звук и `prefers-reduced-motion` не мешают прохождению.

Перед завершением изменения выполняются:

```bash
npm run typecheck
npm run lint
npm test
npm run test:e2e
npm run build
```

## 16. Запрещённые упрощения

Не допускаются:

- неподвижный персонаж, не связанный с действием;
- растровые буквы и ответы внутри изображений;
- управление только мышью или только drag-and-drop;
- объекты, выходящие за сцену после resize;
- CSS-вращение 3D-персонажа вместо подготовленных ракурсов;
- язык или луч, появляющийся сбоку и не связанный с точками начала и цели;
- бесконечные сообщения и неочищенные таймеры;
- звук без визуальной обратной связи;
- публикация незавершённой игры как макета;
- зависимость запуска от сети;
- публикация, remote или GitHub Actions без прямого запроса пользователя.

## 17. Критерий готовности новой игры

Новая игра соответствует серии, если:

- имеет уникальную учебную механику;
- содержит 10 проходимых заданий без повторов;
- персонаж выполняет осмысленное действие;
- есть изображения, музыка и набор эффектов;
- работают мышь, клавиатура и touch;
- сцена корректна от `360 px` до desktop и после смены ориентации;
- отключение анимации или звука не ломает прохождение;
- результат записывается только после завершения;
- все обязательные тесты и production-сборка проходят.
